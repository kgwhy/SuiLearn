## 背景

当前工作流已经要求 `base_ref`、允许文件、测试命令和 diff 范围，但对“配置类小改动”的语义验证不够具体。Docker/本地混合启动场景中，配置解析通过并不代表浏览器、Nginx、Spring CORS、宿主机端口和容器网络边界都通。

## 决策

1. 新增配置 / 启动 / 集成类附加门禁。
   - 覆盖端口、CORS、Docker/Compose、反向代理、环境变量、CI wrapper、数据库连接和第三方服务地址等。
   - 这类任务可仍按风险判定 Tiny/Normal/Major，但不能跳过验收矩阵和运行态验证。

2. 把“兼容”显式拆成默认行为和覆盖行为。
   - Spec 中必须写清楚“默认无需配置”还是“可通过环境变量切换”。
   - 如果用户要求无需手动切换，验收标准不得只写“可配置”。

3. 同一问题链路只使用一个 active change home。
   - 开始修改前搜索 active changes。
   - 后续修复同根因链路时追加到主 change 的 tasks / verification。
   - 无关功能 change 只能引用主 change，不能复制 Docker/配置验证细节。

4. 运行态验证优先于静态验证。
   - 静态命令用于证明展开结果。
   - 运行态命令用于证明真实边界，包括浏览器等价请求、预检请求、容器环境、服务健康或 CLI 实际调用。

5. 第一次返工触发 Spec 回路。
   - 如果用户指出“语义不对”“不是这个效果”，或者验证暴露默认行为不符合要求，必须先更新 Spec/任务验收，再继续实现。

## 风险

- 门禁过重可能让真正的 Tiny 文档改动变慢。缓解：规则只针对配置 / 启动 / 集成类变更；纯文案或单文件非运行态配置可记录“不适用”。
- 运行态验证可能受本机服务状态影响。缓解：若不可运行，必须写明不可用原因，并提供等价的最小复现或手工验证清单。
