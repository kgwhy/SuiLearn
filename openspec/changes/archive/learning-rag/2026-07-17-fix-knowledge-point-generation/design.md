## 上下文

后端已通过 `POST /materials/{materialId}/knowledge-point-generations` 提供持久化知识点生成，旧同步提取端点仅为兼容而保留。Web 工作台仍调用旧端点。`KnowledgePointService` 会校验完整、基于证据的模型输出，却直接抛出 schema 校验失败；适配器只要求通用 JSON，尚无结构化修复路径。

这是一个 Normal 级跨角色变更。Server Backend 负责 `services/api/**`，Web Frontend 负责 `apps/web/**`，Test 负责对应测试，Reviewer 审查已批准变更。由于持久化端点与任务字段已有契约，无需修改 OpenAPI 或数据库 schema。

## 目标与非目标

**目标：**

- 在校验前接受与标准格式无损等价的 OpenAI 兼容 JSON 表达。
- 对无效结构化响应发起一次有限、带诊断信息的修复请求。
- 修复尝试失败后持久化安全的 `FAILED` 任务结果。
- 让 Web 使用并展示持久化生成任务。

**非目标：**

- 不在本地补造内容或引用，不使用关键词 fallback，也不持久化部分知识点。
- 不修改 Provider 传输层重试、任务持久化 schema、端点路径、Android 或正式 OpenAPI 契约。
- 不为诊断存储或暴露原始模型输出、完整资料正文。

## 设计决策

### 将语义修复与传输重试分离

现有适配器重试只处理暂时性 HTTP/IO 故障。仅在一次原本成功的响应未通过结构化输出校验后，增加一次语义修复尝试。该策略是确定性的：初始响应加至多一次修复响应，与 `adapter.max-retries` 无关。

增加通用传输重试无法修复无效 JSON 语义；无限修复会增加成本并可能形成循环。立即失败成本更低，但无法处理可恢复的 Provider 格式差异。

### 仅归一化封闭集合中的无损差异

适配器会在解析前移除 JSON fence；仅当规范字段不存在时，将已记录别名映射为规范字段，例如 `knowledge_points` 到 `knowledgePoints`、`summary` 到 `shortSummary`、`applications` 到 `applicationScenarios`。不得推导 `principles`、`pitfalls`、引用、revision ID、block/page 位置或 excerpt。

别名归一化必须受限。泛化的“尽力转换”可能悄悄生成有误导性的 DRAFT，或削弱来源可追溯性。

### 依据校验原因修复，但不持久化原始输出

校验返回有限、面向用户安全的 schema 失败类别（例如缺少 `citations`，或引用不属于所提交证据）。修复请求携带原始生成上下文及这些失败名称，并要求返回完整替换的 JSON 对象。首次响应原文和来源正文不得写入任务错误、数据库记录、API 响应或日志。

将完整原始响应传给修复提示可帮助部分修正，但会扩大敏感数据处理与提示注入攻击面。修复请求改为依据已受控的证据上下文重新生成。

### 持久化任务承载用户可见失败

`submitGeneration` 与消费者调用同一生成服务。首次或修复响应仍无效时，任务以稳定的 `AI_STRUCTURED_OUTPUT_INVALID` 和脱敏说明标记为 `FAILED`。消费者在该终态后正常完成，而不是重新抛出预期的模型质量失败。非预期 Provider/传输故障继续沿用现有持久化重试/失败路由。

### Web 只提交任务而不等待生成

资料提取操作将调用 `generateMaterialKnowledgePoints`、保存返回任务状态并刷新任务/资料数据。工作台现有任务状态卡负责展示最终结果。这会从主要 UI 路径中移除已弃用同步请求，避免预期的生成失败变成 HTTP 500 toast。

## 风险与权衡

- [Provider 响应使用了未支持但无害的别名] → 保持归一化别名表显式，并为每个受支持别名添加测试；未支持变体在一次修复后安全失败。
- [修复重试增加 AI 延迟/成本] → 限制为一次请求，且只在结构校验失败后触发。
- [错误引用可能指向无关来源] → 保留现有证据白名单校验，不持久化部分草稿。
- [任务错误泄露模型/资料数据] → 仅由校验类别构造错误消息，并测试其中没有原始输出。
- [旧客户端仍调用同步端点] → 保持兼容，但让 Web 主路径使用持久化端点；契约弃用标记留待单独移除变更处理。

## 迁移计划

1. 部署后端校验/修复处理与测试；不需要数据迁移。
2. 仅为 `AiProvider` 接口兼容调整现有非生产 runtime fixture 与测试替身；不新增、启用或扩展 runtime fixture。
3. 基于已存在端点部署 Web 任务提交改动。
4. 在聚焦测试和任务 UI 中验证有效结果、可修复无效结果、两次无效结果。
5. 回滚时撤回 Web 调用方和后端代码；已标记 `FAILED` 的任务仍是审计安全的终态记录。

## 待确认问题

无。用户已批准“一次修复请求，随后任务失败”的策略。
